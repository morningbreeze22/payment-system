Event-Model Design (Alternative B) — Interactive Guide

Explains event-model-design/event-model-v2.md + 01-event-table-schema.md. Status: PROPOSAL — the adopted baseline remains requirment-v4.md. Companion: event-model-playground.html (step through real scenarios).

One sentence

The baseline stores current state and updates it; the event model stores what happened and computes current state. Both designs implement the same business semantics (requirment-v4 §4/§6/§7/§9/§10 — amounts, evidence precedence, release rights, trust-age, escalation). What differs is the storage model and where safety mechanisms live.

The four structures

StructureKindRole
PAYMENT_EVENTappend-only THE authorityEverything that ever happened to a payment; per-payment total order via a dense VERSION. Rows are permanent (archival was removed after review proved it a defect factory — §9).
PAYMENT_HEAD1 mutable row per paymentWrite-serialization lock, money witness (REQUIRED / PAID_TOTAL / RESERVED), one-open-request backstop, scanner/UI index. Updated in the append transaction; rebuildable from the stream; can veto a write, never authorize one.
TRADE_HEAD1 mutable row per tradeTWO snapshot watermarks, each with digest + pointer: accepted (newest VALID snapshot = trade truth) and seen (newest processed at all). The fan-out equality fence checks SEEN.
INBOUND_EVENT_INBOXUNIQUE(source, event_id)Dedup of FEED deliveries only, atomic with processing. Snapshot deliveries need no inbox — admission + seq guards make redelivery converge.

Everything else — required amount, paid, reserved, phase, markers, retry state, MAYBE, parked, escalation — is derived by the fold. There is no stored authoritative state machine, no mutable request row, no separate projection table, no transition journal (the stream IS the history).

Where it came from

The runnable tl-proposal-proof suite in this repo proved an append-only core CAN satisfy the money-safety scenarios provided it carries the full guard set. A v1 draft scaled that up; the v2 refactor closed every CRITICAL/HIGH item v1 ranked; then 32 external adversarial review rounds (24 CRITICAL / 44 HIGH / 12 MEDIUM / 5 LOW findings, every one folded) ended on a clean round. The remaining gap against the baseline is implementation evidence (fold golden vectors, real-Oracle trigger proofs — 00-README items 2–7), not design rounds.

PAYMENT_EVENT — one table, self-describing history

One row per fact. The interesting columns:

Identity & order

PAYMENT_KEY — the canonical scope tuple business_id|payment_type|debit_account|currency. The encoding is identity input: byte-exact spec, golden vectors, ONE shared encoder, injective by rule (no | in components; encoder fails closed).
VERSION — dense fence slot, the stream's total order; allocated as LAST_VERSION+1 under the head lock.
REQUEST_ORDINAL — which request the event concerns. Identity = hash(scope | ordinal), so a DB restore + replay regenerates the SAME keys and the engine rejects the collision (the baseline §5.2 runbook applies unchanged).

Schema-claimed identity (generated columns)

IDEM_CLAIM — generated: the idempotency key, only on REQUEST_OPENED. UNIQUE ⇒ two openings can never carry the same key, whatever writer or bug produced them.
ORDINAL_CLAIM — generated: key#ordinal, only on openings. UNIQUE ⇒ ordinal reuse collides loudly.
UETR uniqueness lives on the head (PH_UETR_UQ) because an event-level claim missed the query/feed channels and refused a legal CT-dedup re-recording.

Money & evidence

AMOUNT — the event's own number (required amount, request amount, outcome amount restated, settled amount, mismatched amount). Money facts carry their numbers — the fold aggregates, never infers.
EVENT_CODE — the structured classification the fold branches on, recorded at decision time (the CA-1 mapping), never re-derived later from raw PROVIDER_CODE.
EVIDENCE_SOURCE — SYNC_RESPONSE / QUERY / FEED / OPS / SYSTEM; precedence rules key on it.

Guard-stamped facts

TX_ID — stamped by the guard trigger with the local transaction id; writers cannot supply it. This is how the dual-control pair proves same-transaction membership in the database.
CREATED_AT — also guard-stamped, UTC only (SYS_EXTRACT_UTC): an immutable episode anchor may never be writer-supplied. Set-once timestamps come free with immutability — the clock-discipline problem disappears.
APPROVAL_REF — typed dual-control approval id; free text in DETAIL binds nothing (the fold never reads DETAIL).

Immutability is enforced, not promised

Grants: application role has INSERT and SELECT only.
A guard trigger raises on ANY UPDATE or DELETE —
history is immutable against every writer, including humans in an incident.
Rows are PERMANENT: no archival path exists (removed by review, §9/§10);
partitioning (index-maintaining DDL only) is the only sanctioned tiering.

The shape matrix — every cell is a CHECK

For every type, every governed column is either Required, must-be-NULL, or Optional — and each row becomes ONE generated CHECK constraint. Two hard-won rules:

Oracle three-valued logic bites

A bare CHECK (EVENT_CODE IN (...)) evaluates UNKNOWN on NULL and silently passes. Every classified type's check carries an explicit EVENT_CODE IS NOT NULL. This lesson was re-learned twice during review (rounds 1 and 13) — it is now a derivation rule, not a convention.

The constraint set is generated, not hand-written

The complete 19-constraint set is a build deliverable: generated from the matrix by a small tool and proven equal to it by a parity self-test (every R/N/O cell exercised by an insert-must-fail / insert-must-pass pair). Comments and Markdown enforce nothing; only the generated set does.

The only write path — six steps, one transaction

Every writer — intake, scanner, resolver, feed handler, ops surface — goes through the same protocol. It is the baseline's own lock-then-write idiom (a pessimistic head lock replaced v1's optimistic fence-retry loop). Click Step to walk through it.

1
Lock the head
SELECT … FOR UPDATE on PAYMENT_HEAD (insert-on-first-contact: LAST_VERSION=0, NEXT_REQUEST_ORDINAL=1, REQUIRED_AMOUNT=NULL — explicit initial values, never NULL+1 arithmetic). Serializes all writers per payment.
2
Fold the stream
Read PAYMENT_EVENT by (key, version); compute required, paid_total, reserved, markers, open ordinal — the pure function.
3
Witness check (fail closed)
Fold money outputs must equal the locked head row — required, paid, reserved AND open ordinal, NULL-safe. ANY mismatch: abort with NO decision, page, quarantine (PHASE=WITNESS_DIVERGED). A veto, never an authorization.
4
Decide
Pure function: fold state → list of events. All business semantics (inherited from v4) live here and in the fold — testable with golden vectors, no DB needed.
5
Per-event: INSERT, then head effect
Each event inserts at LAST_VERSION+1, THEN applies ITS head effect (CAS / witness change / phase). Per event, not batched — the backstops check each insert against the head state its predecessors left behind.
6
COMMIT
Multi-event decisions (outcome + successor, enrich-fail + outcome) are ONE atomic transaction.
The write path in one line: lock → fold → witness-check → decide → append+effect per event → commit. Use Step to see what each stage protects.

Why per-event, not batched?

The atomic outcome+successor decision is legal only in this interleaving: outcome insert (its ordinal still open) → close CAS (column goes NULL) → successor REQUEST_OPENED insert (trigger sees NULL) → open CAS. Batching all inserts before one head update would make the backstops reject the design's own legal writes. This defect was found while re-deriving the design and fixed before any review round.

Two independent failure nets

The fence — PE_FENCE_UQ UNIQUE(payment_key, version): any writer that bypasses the lock collides and fails loudly instead of forking history.
The witness — if head and fold disagree, nothing writes; the payment quarantines as WITNESS_DIVERGED, scanners skip it, and repair is the head-rebuild runbook. If rebuild doesn't clear it the stream itself is in dispute — only the dual-control door resolves it (that door alone runs in RECORDING mode under divergence, proceeds on the fold, and rebuilds the head in the same transaction).

The write-ahead discipline, inherited and sharpened

The fold — aggregation, never inference

required_amount = AMOUNT of the REQUIRED_AMOUNT_SET with highest UPSTREAM_SEQ
authoritative_outcome(ordinal)
                = the LATEST outcome-class event (OUTCOME_RECORDED or SETTLED)
                  for the ordinal in stream order — a PLATFORM_VERIFIED_* outcome
                  appended through the dual-control door SUPERSEDES what it corrects
paid_total      = Σ AMOUNT over ordinals whose authoritative outcome is
                  executed-class (EXECUTED | PLATFORM_VERIFIED_EXECUTED | SETTLED)
reserved        = AMOUNT of the open request, else 0
shortfall       = required − paid_total − reserved      ← the standing-rule input

Because the inputs are literal recorded numbers, deploying a changed fold cannot retroactively change a settled payment's money totals unless the aggregation itself changes — which is exactly what the deploy gate catches.

Try it — toggle events, watch the fold

A tiny in-page fold over one payment's stream. Toggle rows on/off (as if they existed or not) and see what the pure function computes. Note what toggling does NOT do: no stored state was ever edited.

Fold governance — the two standing controls

1 · Deploy gate (before any fold change ships)

Re-fold EVERY payment stream with a head row — open AND terminal, no sampling, no exclusions (events are permanent, so the full population is always foldable) — and compare against the head witness. Any money-field difference pages and blocks the deploy. A sampled gate provably lets a terminal-stream fold defect deploy silently and later reopen a phantom shortfall. At ~3,000 trades/day the full population is minutes of work.

2 · Drift scan (continuous)

A scheduled job re-folds open payments and compares fold output to the head witness; mismatch pages. This is the same two-bookkeepers control as the baseline's I1/I2 scan: the head is maintained by simple mechanical increments, the fold by rule evaluation — two independent computations of the same money.

What a fold deploy CAN still change: control-state interpretation (marker liveness, retry pacing — not money). This is accepted in the honesty box as the same risk class as any code deploy in the baseline; the deploy gate bounds the money side to zero.

The guard inventory — what the database itself refuses

All of these are independent of fold correctness: schema constraints, head CAS row-counts, and BEFORE-INSERT trigger backstops (implemented as ONE compound trigger validating each single-row insert at after-statement time; a statement guard forbids multi-row inserts so Oracle's mutating-table restriction never bites). Fence PE_FENCE_UQ

UNIQUE(payment_key, version) — the backstop against lock-bypassing writers.

Kills: two writers extending the same stream concurrently forking history. A collision seen while HOLDING the lock means the head lost sync — page, rebuild from the stream.

Identity write-once PE_IDEM_UQ / PE_ORDINAL_UQ

Generated-column uniques on opening events.

Kills: two openings with the same idempotency key (double-spend of a key) and ordinal reuse splitting the per-ordinal aggregation — whatever writer, path, or bug produced them.

One open request §6.2 CAS

Opening CAS: WHERE OPEN_REQUEST_ORDINAL IS NULL AND NEXT_REQUEST_ORDINAL = :ordinal; row count 0 aborts.

Kills: two concurrent open requests (the single most dangerous invariant) — a second bookkeeper that does NOT trust the fold. The head's open key/amount are copied FROM the opening event row, never from a program variable, so the wire key is transitively bound to the schema-claimed key.

Opening amount = shortfall §6.3

:new.AMOUNT = REQUIRED_AMOUNT − PAID_TOTAL on the transaction-fresh head.

Kills: a wrong decision opening for MORE than the shortfall — without this, every downstream gate (reservation copy, key echo, terminal equality, close CAS) would faithfully carry the oversized amount to the wire and book paid 180 against required 100.

Amount equality on every outcome §6.3

Outcome/SETTLED for the open ordinal require AMOUNT = RESERVED; through the closed-ordinal door, = that ordinal's OWN opening amount.

Kills: false history — a reject recording amount 999 for a 100 request, or a 90-settlement booking as a 100-execution. A differing feed amount is only insertable as SETTLEMENT_MISMATCH_RECORDED (routing enforced). The money-terminal close CAS also carries AND RESERVED = :amount — the witness binds at what NUMBER the ordinal closes.

Key echo §6.3

POST_STARTED / POST_RESULT / QUERY_RESULT require IDEMPOTENCY_KEY = OPEN_IDEMPOTENCY_KEY.

Kills: stale evidence for an EARLIER request's key being recorded against the current one, and an attempt event citing a key other than its opening's.

Open-ordinal gate §6.3

Attempt/evidence/outcome events require their ordinal to BE the open one; terminal evidence against a closed ordinal must route to the contradiction park.

Kills: a feed rejection recorded against a closed executed ordinal without a park; a query result attaching a first UETR claim to a never-opened ordinal; a mismatch against a closed ordinal committing as a free-standing park with no exit.

Release rights §6.3 · unified predicate

CANCELLED_NOT_SUBMITTED / SUPERSEDED_OPS require provably NOT SUBMITTED — defined in exactly TWO places (v2 §5.3, 01 §5); everywhere else cites it.

Kills: one wrong "it was never sent" decision after a crash releasing an executed request's reservation — the successor then pays a second time. The predicate: zero POST_STARTED, OR latest attempt closed by a synchronous BUSINESS/DEFINITIVE reject with no later attempt AND no acceptance-class row post-dating it (a delayed query ACCEPTED proves SUBMITTED and revokes releasability). Four review rounds of drift came from restating it — hence define-once-cite-elsewhere.

REJECTED_PROVIDER needs real evidence §6.3

Requires a same-ordinal TERMINAL-class negative evidence row post-dating the latest attempt. BUSINESS_REJECT never qualifies.

Kills: attempt 1's stale retry-class reject terminally closing attempt 2's lost-response execution. Retry-class negative facts expire the moment a later attempt starts.

Downgrade gate §6.3

DOWNGRADED_FOR_REPOST requires NOT_FOUND post-dating the latest attempt AND no acceptance-class row post-dating that attempt.

Kills: downgrading an ACCEPTED request (the backward transition the baseline forbids). Recency alone proves recording order, not the absence of acceptance — the second conjunct was a review find.

Dual-control pair gate §6.3 · TX_ID

Every PLATFORM_VERIFIED_* outcome requires the row at VERSION−1 to be its OPS_VERIFIED_OUTCOME_APPLIED — same ordinal, same TX_ID, equal APPROVAL_REF.

Kills: a solo "verified" outcome booking money with no approval, and a dangling approval committed earlier being paired later. Same-transaction membership is DB-checked via the guard-stamped TX_ID, not promised by the application. The closed-ordinal case is additionally the ONLY write admitted for a closed ordinal.

UETR association §6.3 + PH_UETR_UQ

ONE association relation (UETR-bearing events ∪ permanent RECONCILED_BY_KEY rows); an event's UETR must match its ordinal's association or be the first claim anywhere. PH_UETR_UQ = the belt for simultaneous first claims.

Kills: a resolver re-attaching ordinal 1's UETR to open ordinal 2 (letting ordinal 1's stale feed reject release ordinal 2's reservation); a claim of an abandoned historical UETR; two heads silently sharing one UETR (platform contract violation becomes a loud constraint failure, never a silent double-booking).

Version continuity §6.3

:new.VERSION = LAST_VERSION + 1; head effect advances LAST_VERSION; drift scan asserts density.

Kills: skipped slots — the fence rejects duplicates but not holes. COUNT(*) = MAX(VERSION) = LAST_VERSION.

Opening stamp §6.3

REQUEST_OPENED requires REQUIRED_AT_OPEN = REQUIRED_AMOUNT on the transaction-fresh head.

Kills: the immutable UI amount-series stamp being born wrong — display-only, but unfixable if wrong (immutability cuts both ways).

Key/business binding PH_BIZ_BIND_CK

BUSINESS_ID must equal the key's leading component; the key must contain exactly three delimiters.

Kills: a mis-bound head dropping out of its trade's fan-out worklist and skipping an absence-cancellation; and non-injective key encodings merging two real payments into one head.

Delivery fidelity inbox trigger, §8

Two universal fold-state-free rules on every feed-delivery transaction: no class inversion; no witnessless no-op.

Kills: a SETTLED delivery being recorded as a rejection (or laundering a 90-mismatch into a clean 100-rejection), and a disagreeing delivery being silently no-opped past the contradiction park. Mandatory statement order: event inserts first, terminal inbox write LAST (triggers fire at statement time).

Honesty box: full temporal legality beyond this set stays code-enforced — fold logic under golden vectors. The backstopped subset covers the money-moving transitions; the residue is the same class as a wrong CAS in the baseline.

Snapshot admission — two watermarks, serialized at the trade

Feed deliveries — inbox, matching, and the two exits

Atomic seen-and-processed

The inbox INSERT (UNIQUE(source, event_id)) rides the SAME transaction as the append it causes — or the same transaction that decides "benign no-op" (agreeing or stale evidence). A crash before commit leaves neither; redelivery hits the dedup or re-runs cleanly. Snapshot deliveries get NO inbox row at all.

Three-source matching, fail-closed multiplicity

Candidates = DISTINCT payments from head matches ∪ event-index matches ∪ RECONCILED_BY_KEY rows, all always consulted. 0 → durable UNMATCHED_TERMINAL row, level-triggered paging. 1 → lock, RE-RUN the union inside the transaction, then fold + append. 2+ at any point → CRITICAL, nothing committed. The post-recheck race dies on PH_UETR_UQ — a schema fact, not a promise.

Exit 1 — RESOLVED_HANDLED

The re-match found the payment; whatever the write path decides (append, contradiction park, benign no-op) is governed SOLELY by the normal gates under the head lock — a correspondence-verification relation was built, proved to be a diverging second implementation of write-path legality, and retracted. The inbox row keeps an audit pointer (payment key + head version at handling).

Exit 2 — RESOLVED_DISPOSED

For evidence that CANNOT go through a write path: FOREIGN (not ours) or RECONCILED_BY_KEY (the lost-UETR settlement — response timed out, key-query recovery carried no UETR, no stream will ever contain it). Reconciliation names payment + ordinal, locks the named head, verifies the stream ALREADY agrees (class and amount), binds the four-eyes approval to the stated claim, and sets the head's UETR slot. If the stream disagrees, disposal FAILS — truth enters through the dual-control door first. These rows are PERMANENT: they carry an association recorded nowhere else.

Delivery-fidelity backstop (universal, fold-state-free, on every feed transaction): (1) no class inversion — a SETTLED delivery cannot produce rejected-class records, a REJECTED delivery cannot produce executed-class bookings, a MISMATCH delivery can only produce mismatch/contradiction rows; (2) no witnessless no-op — handling a terminal delivery with NO append requires the associated ordinal's authoritative outcome to agree in class (and amount, for settled/mismatch). The transcription residue (delivery → EV columns) is the inherited CA-1 recorded-at-the-time class: one shared, golden-vector-tested transcriber.

The one manual door for possibly-moved money

Diagnosis: head for "where", stream for "why"

fold --explain <payment_key>

Prints the stream and the fold's state after each event — the event model's answer to "SELECT the state". Ships with the MVP as a deliverable, not a nice-to-have (honesty box item 6). The stream IS the transition history the baseline lacks locally; the team must learn to read it.

No privileged writer, ever

Ops actions arrive through the SAME write path as everything else: marker clear and retry re-arm (the two money-enabling single actions) carry a typed four-eyes APPROVAL_REF, consumed by CAS. Blocking and annotating bind nothing. Rogue-SQL arguments are out of scope by the PO standard — the front door is what gets reviewed, and every front door goes through the gates.
