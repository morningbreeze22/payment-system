Event-Model Walkthroughs — the PAYMENT_EVENT table, row by row

Every scenario from the state playground, replayed as actual table rows. Each step INSERTs the highlighted row(s); · means NULL; the TX column shows which rows landed in one transaction (consecutive fenced slots, atomic). Below the table, the fold — derived state literally recomputed by this page from the rows above after every step. Nothing below is stored anywhere.

(arrow keys work too)
Column key: TX = which step/transaction inserted the row · V = the fenced version slot (UNIQUE per payment — the serialization point) · ORD = upstream ordering (strictly-newer guard) · IDEM_KEY = idempotency identity, allocated by the REQUEST_OPENED row's slot and echoed on that request's later rows · HASH = payload hash, durable BEFORE the wire · UETR / PROV_REF / CODE = provider evidence · SRC = evidence channel · ACTOR = who appended (every writer uses the same fence, humans included) · IDEM_CLAIM = generated column: only REQUEST_OPENED rows populate it, UNIQUE — identity is write-once in the schema · AT = illustrative clock · DETAIL = display/audit text (the fold never reads it).
