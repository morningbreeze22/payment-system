Every transaction decision in this design comes from three rules

A

One lock owns the money

your requirement — “we can never mess up amount calculation”

Rule A is a two-layer protocol, and both layers run in the same transaction. Layer 1: all money arithmetic — shortfall checks, request creation, overpay detection, completion — happens under the obligation row's SELECT … FOR UPDATE, one session at a time, never from a moving picture. Layer 2: the money movement rides a CAS on the request row (WHERE outcome IS NULL, WHERE stage_state = 'READY'…), so the event that moves money can fire exactly once. A1 shows why arithmetic needs the lock; A2 shows why the lock alone still double-moves money without the CAS.

INCREMENT committed

In the same transaction that inserts the request row. Shortfall instantly sees in-flight money — the double-pay window never exists.

DECREMENT committed · INCREMENT confirmed

Decrement rides the CAS that sets a terminal-negative outcome; confirmed moves when EXECUTED evidence is applied. Each exactly once — the CAS row count guarantees it.

NO MOVEMENT

At POST time, on the POST response, on retries, at claim time. No counter mutation is ever adjacent to an external call.

But there's a tension. If everything money-related needs this one lock, and enrichment or an engine call can take seconds — does the lock get held for seconds? Never. That's rule B.

B

Nothing slow ever runs inside a transaction

your requirement — “enrichment calls take time, so we claim with CAS”

Every slow thing — enrichment lookups, the engine POST — follows one shape: a short transaction to claim the row (a lease), commit, do the slow work with no transaction open and no locks held, then a short transaction to CAS the result in. For the POST that means one attempt = two transactions with the wire in between — and the gap between them is where all the interesting failure design lives.

Reference: the claim CAS these animations keep running 
UPDATE payment_request
SET    stage_state = 'CLAIMED',
       claimed_by = :worker,
       claim_expires_at = :now + :lease,
       attempt_count = attempt_count + 1,
       last_post_attempt_at = :now
WHERE  payment_request_id = :id
  AND  stage = 'POST' AND stage_state = 'READY'
  AND  outcome IS NULL
  AND  divergent_payload_at IS NULL
-- rowCount 1 = claim won · 0 = lost race, skip

Before TX1 commits, the row also records the write-ahead facts: last_sent_hash, divergence_expected, last_post_attempt_at, post_attempt_seq. (The deterministic key is computed and stored at row creation — K-02 — and re-verified/persisted-if-absent at the first posting claim — K-04/§11; never minted at send time.) The DB durably knows what may be sent before any byte leaves. The §14.1 journal's ATTEMPT_STARTED insert (the content write-ahead) rides this same commit; ATTEMPT_RESOLVED rides the episode-ending commit.

Rules A and B assume threads race constantly — for the same claim, the same obligation, the same trade. What keeps racing threads from deadlocking or double-doing work? Rule C.

C

Fixed lock order, stated expectations

the rule that lets A and B survive racing threads

Two disciplines, applied to every single write. Order: locks are always taken trade → obligations (sorted tuple order) → request, so a wait cycle — deadlock — is structurally impossible. Verdicts: every state change is a conditional UPDATE whose WHERE restates the expected world; rowCount = 1 means you won, 0 means someone beat you — skip, never retry blindly.

  1. Scanners select candidates with no locks at all. A plain bounded read: dimension predicates, DB time, deterministic order. It may return stale rows — the next step catches it.
  2. Per candidate, fresh transaction: obligation lock first, then the claim CAS. The CAS WHERE restates the full expected state. Row count 0 = another worker won — skip (that's C1 exactly).
  3. Per-item transaction boundaries. One poisoned item fails alone; it can never take the batch down with it.

You've now seen all three rules in isolation. The intake flow is where they run together, on every single message.

Σ

Intake: all three rules in one flow

your requirement — “only check minimal fields before saving the obligation”

A trade snapshot carries 0..N payment blocks. Admission is one transaction; then each block gets its own transaction — there is deliberately no cross-obligation transaction, because redelivery plus per-block ordering guards is the convergence mechanism. And your minimal-fields rule is rule B applied to intake: the obligation needs only its 4 valid scope-key fields (its identity) to be written. Party and account validation is slow, failable work — it belongs in the enrichment lease afterwards, retriable per request, never inside the intake transaction. The three Σ scenarios run whole lifecycles: multiple requests on one obligation, out-of-order snapshots, and asynchronous evidence colliding with intake.

rule B: slow validation deferred to the enrichment lease
The Kafka offset is acknowledged only after commit — at-least-once redelivery plus ordering guards is the convergence mechanism. Validation is a whole-snapshot verdict (§6.0/§6.6): a snapshot that fails it applies no amounts at all — instead every extractable scope gets its anchor row / validation marker (required NULL + validation_failed, watermark NOT advanced) so the payments stay visible while nothing half-applies. Obligation saving needs only the 4 valid scope-key fields; deep per-payment validation is enrichment's job, never intake's.
§

Ops corner & where the spec lives

Shutdown follows rule B's logic (§11): stop Kafka listeners → stop scanners → drain in-flight POSTs → release only the ENRICH claims this worker holds. POST claims are never released on shutdown — a POST may be mid-flight; lease expiry into MAYBE is the only exit (that's B3).

Short transactions that state their expectations, one pessimistic lock that owns all arithmetic, a fixed lock order, everything slow pushed outside transactions behind a lease — and MAYBE_SUBMITTED as the honest name for the one gap that can't be closed.
