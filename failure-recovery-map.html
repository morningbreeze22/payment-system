Gaps found by this walkthrough (folded into §18)

GAP-1 → upstream ask 6: scope-key provenance in writing — payment_type / debit_account / currency are message-carried stable identifiers, never derived via a pre-intake lookup. The scope key (§2.1) and the deterministic idempotency key (§5.1) depend on it.

GAP-2 → upstream ask 7: a never-emitted upstream message is the one lost-payment class with no local detector — upstream must confirm emit-failure monitoring or provide a count-recon signal.

GAP-3 → §20-10 + console O12 (revised 2026-07-11): §6.7's "manual application" of a tied amendment had no operation anywhere. Final design leans on the transport contract fact (§6.0: Kafka carries only the snapshot's storage id — the XML lives durably in the upstream-populated store): the tie record carries identifiers + a masked diff, and the REPROCESS-SNAPSHOT operation re-fetches the adjudicated XML by id and re-runs the normal fan-out with the tie condition RECOMPUTED SERVER-SIDE (round 3: no caller-supplied ordering — fabrication impossible, re-runs no-op). No payload in logs or parameters; store immutability/retention = upstream ask 8.

Everything else resolves to an existing designed path, a tracked §18 open item, or a PO-accepted limitation — see the walkthrough §10 verdict.
