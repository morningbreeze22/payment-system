Ops Console — Proposal

SUPERSEDED RENDERING — the current revision is ops-console-proposal.md (v4 baseline); this page is kept for layout reference only Known-stale content below: O4/O5 + the "Parked events" queue are OBSOLETE (no parked-event store exists); state displays should use the §10.4 labels; section refs are v2-era requirment-v2.md §18 2026-07-05 Spring Boot · Oracle · SSO

1 · Why this exists

The orchestrator is deliberately fail-blocked: when it cannot prove an outcome, it parks state and holds money reserved rather than guessing. That is the right design — but every parked state requires a database mutation to leave, and today no tool can execute one:

Dead-end stateProduced byWhat must eventually happen
NEEDS_REVIEW requestretry exhaustion, unmapped provider codes, amount mismatch, aged UNKNOWNretry / reject / supersede — CAS transitions, two of which release the reservation
Stuck reservationrequest stalled in any non-terminal statesupersede/close (v2 §4 makes this a required feature)
Parked feed eventunmatched UETR (v2 §5/§8)replay after investigation, or discard
Aged UNKNOWNPOST outcome unresolvable within max ageon-demand resolver trigger, then resolution
Overpay latchconfirmed > requiredtoday: ignored forever (v2 §13); ops may need to acknowledge/annotate
The interim model — ops reads the card, then acts in other systems — covers investigation but not one of these mutations. Without a console, every occurrence becomes a DBA ticket running hand-written SQL against a payment database: slow, unaudited, and the single most likely source of invariant-breaking writes.

2 · Design principles

  1. No new mutation semantics. Every console action executes the same conditional CAS UPDATE + obligation-lock flow the orchestrator itself uses (v2 §3, §4, §10). The console adds authorization and audit around existing transitions — never a new way to change state. Row count 0 = "state moved under you" = action rejected, re-fetch.
  2. Fail-safe bias preserved. Nothing in the console can create or submit a payment. Actions release, park, or resolve; the only path back to money moving is retry, which re-enters the normal §6.4 retry-guard.
  3. Every action survives DR. No local manual-action or transition-history journal exists (v2 §12; the switch-gated §14.1 attempt-content journal is a separate same-database audit sink and rewinds with a restore), so each action writes the structured log line AND requires an external ticket reference — the record that survives a database restore.
  4. Read wide, write narrow. The read surface shows everything; the write surface is a closed catalog of six operations.

4 · Architecture

┌─────────────┐   OAuth2/SSO   ┌──────────────────┐   same schema   ┌────────┐
│  Ops UI     │ ─────────────► │  ops-console-api  │ ──────────────► │ Oracle │
│  (SPA)      │                │  (Spring Boot)    │  CAS + oblig.   │        │
└─────────────┘                │                   │  lock, read-only│        │
                               │  - queue queries  │  views for lists│        │
                               │  - action executor│                 └────────┘
                               │  - approval store │
                               └──────────────────┘
  • Separate deployable, same database, same transaction primitives — ideally via a shared library module extracted from the orchestrator (payment-core-transitions) so console and orchestrator can never disagree about a transition's WHERE clause.
  • AuthN: corporate SSO (OAuth2/OIDC). Roles: viewer (read-only) · operator (O4, O6, annotations) · approver (second pair of eyes for O1–O3, O5; cannot initiate what they approve).
  • Approval flow: initiator submits action + reason + ticket ref → pending row → approver confirms → execution. Pending approvals expire (24h); the CAS re-check at execution time is the final arbiter, and a row-count-0 rejection is surfaced to both parties.
  • Audit: every submit/approve/execute/reject emits the v2 §12 structured log line with trigger_source = MANUAL_OPS:<operator-id> plus the ticket reference. The console DB keeps only approval-workflow rows (console state, not payment state).

5 · UI surface (three screens)

S1 — Queues dashboard

One table per dead-end state (NEEDS_REVIEW, stuck reservations by age, parked events, aged UNKNOWN, overpay latches). Each row: scope key, business_id, amount, age, last error, deep-link to S2. Oldest-first; badge counts in the nav. This is the screen the v2 §14 alerts link to.

S2 — Payment detail

The full story of one obligation: header (scope key, required/committed/confirmed, derived step status, active exception), request list with status + retry state + UETR, the transition history from the log store (the console reads logs; it does not maintain a journal), and parked events for this scope. Action buttons appear only for catalog states and only for the caller's role.

S3 — Action flow

Modal per action: reason (mandatory), ticket reference (mandatory, validated), and a preview of effect ("SUPERSEDE releases 20.00 EUR reservation; shortfall becomes 20.00; step remains IN_PROGRESS") computed read-only under the same lock → submit → pending-approval state visible on S1.

6 · API sketch

GET  /queues/needs-review | /stuck | /parked-events | /unknown-aged | /overpay
GET  /obligations/{scopeKey}                 → S2 payload
GET  /obligations/{scopeKey}/log-timeline    → from log store
POST /requests/{id}/actions                  {type: RETRY|REJECT|SUPERSEDE, reason, ticketRef}
POST /parked-events/{id}/actions             {type: REPLAY|DISCARD, reason, ticketRef}
POST /requests/{id}/resolve-unknown-now      {reason, ticketRef}
POST /approvals/{id}/approve | /reject

All mutating endpoints: idempotency via the approval-row id; optimistic If-Match on the request version so the UI can't act on a stale view.

8 · Open questions for the PO discussion

  1. Who are the ops users (team, count, existing roles), and what SLA do the queues carry (e.g., NEEDS_REVIEW resolved within one business day — v2 §14 currently only tickets it)?
  2. Is 4-eyes required by policy for O1–O3/O5, or is single-operator with mandatory ticket acceptable?
  3. Which ticket system anchors the audit trail — and is the reference enforceable (validated against its API) or free-text?
  4. Retention for console approval/action records.
  5. May retry (O1) bypass the payment cutoff, or does the cutoff check (v2 §7) always win?
  6. Does the overpay acknowledgement need to be visible on the card (read-model field), or console-only?
